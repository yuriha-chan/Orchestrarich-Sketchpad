# Phase F: stage presentation API

The User directed: "for stage rendering, the UI exposes API and the block should use that API". Stage and timeline are distinct. Stage effects remain execution-owned: blocks create, update and remove their own presentation; the Stage renders UI state and never derives effects from runner state.

Replace block-provided React stage components with typed UI presentation primitives: dialogue card (label, text, confirm), animation preview card (label, duration, fade fractions, playback position/playing), and rectangle on the screen (geometry, unit, RGB). The UI stage store exposes operations to add these primitives and remove them, plus update animation playback. Their identifiers represent presentation instances, not document block identities. The stage renderer dispatches on the UI primitive, not on block kind or the block registry. Existing appearance and media pause/resume, stage-grid resizing, dialog completion, and lifecycle must remain unchanged. The core-facing interface uses only framework-independent types. A future block can call the same UI API without adding a block-kind branch or registering a stage renderer.
