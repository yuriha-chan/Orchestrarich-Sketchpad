# Experiment 1-A: Minimal Execution Engine for Column Barrier Synchronization

## Uncertainties Prioritized in 1-A

- Whether logical time t stops until all blocks in the same column complete.
- Whether "the blocks currently blocking t" can be extracted from the execution engine.
- Whether the barrier still waits for completion when a block receiving a skip request completes early.
- Whether cooperative skip mode's automatic skip fires when the blocks that must complete by the end logical time have become only cooperative skip blocks.

## Smallest Components

- 3 tracks. Blocks have required `start` and `length`, and can span multiple cells.
- Blocks notify completion externally via a timer or click.
- Branches, loops, types, and ownership are not handled.
- Implementation: `src/core/execution/timeline-runner.ts`
- CLI for confirmation: `demo/experiment-1a-column-barrier.ts`, `demo/experiment-1a-skip.ts`

## What Was Confirmed

- `pnpm test`: 34 tests passed.
- `pnpm demo:1a`:
  - At t=0, 3 blocks become running simultaneously.
  - Even when the sound effect (300ms) and animation (800ms) complete, t stays at 0 while the click wait remains.
  - A click advances to t=1, and `next-line` in the next column starts.
  - The names of blocking blocks and tracks are displayed.
- We confirmed that even when Enter is sent first in a pseudo-TTY, t stays at 0 while the animation and sound effect remain.
- `pnpm demo:1a-skip`:
  - `loop-bgm` is 3 cells from 0-3. It does not block the barrier at t=0 or t=1.
  - t=0 is blocked by `click-wait` and `sfx`. Even after `sfx` completes, it is blocked by `click-wait`.
  - A click advances to t=1, and it is blocked by `next-line`.
  - When `next-line` completes, the only incomplete block that must complete by `loop-bgm`'s end time 3 is `loop-bgm` (cooperative skip). At this point an automatic skip request occurs. It does not wait for the end-time barrier at t=2.
  - Even after the skip, the timeline stops at the empty t=2 barrier until `loop-bgm` completes its 200ms fade-out. After completion, t=3.
  - When `s` is sent in a pseudo-TTY, a user skip request reaches the running `click-wait` / `loop-bgm` / `sfx`. `click-wait` and `sfx` ignore it, and `loop-bgm` fades out and completes. The barrier waits at t=0 until `sfx` completes.
- These are confirmations that the reading of design.md 1.1/1.2/1.3/1.4/4.1 was mapped to the implementation. The meaning of the specification was not decided from tests.

## What Was Decided

1. The barrier is judged by "at current time t, incomplete blocks whose end time is t+1". Not by start time.
2. Every block has a required `length` (number of unit cells), and `end = start + length`. Overlap of intervals [start, end) within the same track is prohibited.
3. A user skip request is sent via `requestSkip()` to all blocks running at that moment. It also reaches multi-cell blocks not participating in the barrier.
4. A skip request does not directly cause completion. If the block calls `complete` in `onSkipRequest`, it completes; if not, the barrier keeps waiting.
5. Cooperative skip mode is `cooperativeSkip: true`. For a running cooperative skip block B, when all incomplete blocks whose end time is less than or equal to B.end have become cooperative skip, B's automatic skip request fires once. Blocks in future columns are also included.
6. Automatic firing does not wait for B's end-time barrier. It fires when all non-cooperative blocks that must complete by B.end have completed. If B itself is the last incomplete block, it can fire immediately after start. Multi-cell blocks do not stop intermediate columns.
7. For both automatic skip and user skip, the barrier waits for the block to be "completed". If completion is delayed, t does not advance.
8. Empty columns pass without waiting. A column where only a multi-cell block is running also does not stop the barrier until that block's end time.

## Established Reading of the Design

- design.md 1.1: At the start of t, blocks with start=t are started, and it waits until all blocks with end=t+1 complete. The barrier is judged by end time.
- design.md 1.3: Skip does not directly change logical time. The request is transmitted to running blocks and may be ignored.
- design.md 1.4: For a cooperative skip block B, when the blocks that must complete execution by B's end logical time (incomplete blocks with end <= B.end) have become only cooperative skip, B's skip event occurs automatically. From the barrier definition in 1.1, blocks in future columns are also included in "blocks that must complete by B.end". B itself is also included in that set. This is not a barrier exemption.
- design.md 4.1: A block can span multiple cells. In 1-A, this was confirmed with one-cell blocks (`length` 1) and the 3-cell `loop-bgm`.
- The old "no-wait mode" refers to design.md's "cooperative skip mode" (1.4, 2.9).
- Skip does not directly change logical time (1.3). The barrier waits for the block to be "completed".
- Cooperative skip mode automatically generates a skip event when the condition is met (1.4). It does not mean the barrier stops waiting. Even if a block ignores the skip request, the barrier waits for completion.
- The `end <= B.end` reading, including future/pending blocks, was confirmed by the User's judgment: the implementation is right.
- Every block must specify `length` explicitly; there is no default (User decision).
- A block completed before its end time no longer participates in later barriers or in the cooperative auto-skip set, because it is no longer incomplete (User confirmed that no other reading is possible).
